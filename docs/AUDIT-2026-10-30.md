# Server printing audit

Target: 0.1.4-rc.1. Local implementation verification passed **53 tests, zero failures/errors and zero Checkstyle violations**. Hosted verification and the independent baseline security scan remain pending. No live database, object storage, enrollment or printer was changed.

## Corrected behavior

- Native test-print and enrollment backend replay reuse prepared identities. A consumed enrollment cannot be reactivated by repeating a process.
- Print options, inventory formats/status and event fields are checked before persistence. Claim rechecks the queue's current format capability.
- A later failure retains known submission risk. Reprint requires explicit consent when output might already exist, and retry replay resolves its existing receipt even if the original content has expired.
- Enrollment offers authorized named facility choices, with a host-source option and a named standalone default. Backend validation rejects forged and foreign-tenant selections.
- Print documents can use the existing QQQ S3 storage API with a dedicated printing bucket, tenant namespace and exact job/reference/destination validation. Legacy database documents remain readable.
- Durable upload intents and exact orphan cleanup account for failed uploads/queue commits. Cleanup commits each confirmed document removal independently. A renewable lease prevents normal overlapping maintenance; all work reuses a single connection and passes real one-/two-connection pool concurrency regressions.
- Native administration exposes the default 365-day policy, read-only storage scope, backlog and last cleanup result. A host scheduler runs bounded batches every five minutes. Age starts at server-observed successful completion; active, failed, uncertain and unknown-completion jobs remain protected.
- Release publication requires build/security/CodeQL checks, verified artifact promotion and build provenance. Packaged QBit metadata uses the JAR's real Implementation-Version.

## Evidence and migration

The gate exercises real H2 persistence and bounded pools, QQQ StorageAction with an in-memory backend, native process review/resume, current-session record security and real QApplicationJavalinServer route registration/authentication over loopback. Failure tests cover partial upload/deletion recovery, per-document commit boundaries, conflicting/foreign references, destination retargeting, overlapping cleanup and original-content expiry during retry replay. The built JAR manifest reports 0.1.4-rc.1.

Schema initialization adds consumed-enrollment receipts, storage references/content availability, completion timestamps, retention settings/lease and upload intents. Existing inline bytes are retained; completion dates are backfilled only from durable successful events. No automatic inline-to-S3 copy or live purge occurs. Schema changes should be qualified against a backed-up deployment database before rollout.

## Remaining boundaries

Live S3 endpoints, IAM/bucket policies, external bucket users, PostgreSQL, multi-node lease-expiry behavior, production scheduler execution, remote TLS deployment and sustained 10,000-print/day throughput are not qualified by these tests. SQL and object deletion are not one transaction; crashes between them require idempotent recovery. S3 versioning and unfinished multipart parts have separate lifecycle semantics. See [storage and retention](STORAGE-AND-RETENTION.md).

The independent deep scan covers the frozen pre-audit baseline, not the subsequently added storage feature. Two implementation agents independently reviewed the new storage boundaries and added regressions, but that does not substitute for a completed security scan or prove absence of defects. No numerical quality score is assigned.
