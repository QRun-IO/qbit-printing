# Server printing audit

Target: 0.1.4-rc.1. Current local implementation verification passed **72 tests, zero failures/errors/skips and zero Checkstyle violations**. The independent baseline scan and subsequent source remediation reviews are complete. Earlier audit and CI guard commits passed hosted checks; the latest S3 correction requires fresh hosted verification. No live database, customer bucket, enrollment or printer was changed.

## Corrected behavior

- Native test-print and enrollment backend replay reuse prepared identities. A consumed enrollment cannot be reactivated by repeating a process.
- Print options, inventory formats/status and event fields are checked before persistence. Claim rechecks the queue's current format capability.
- A later failure retains known submission risk. Reprint requires explicit consent when output might already exist, and retry replay resolves its existing receipt even if the original content has expired.
- Enrollment offers authorized named facility choices, with a host-source option and a named standalone default. Backend validation rejects forged and foreign-tenant selections.
- Print documents can use the existing QQQ S3 storage API with a dedicated printing bucket, tenant namespace and exact job/reference/destination validation. Legacy database documents remain readable.
- Immutable S3 bindings include the reviewed physical key layout and host separator. Ordered JSON preserves component boundaries, including multiline base paths. Incompatible historical content is rejected before reads, new retry reservations or cleanup; document availability and accounting remain intact.
- Durable upload intents and exact orphan cleanup account for failed uploads/queue commits. Cleanup commits each confirmed document removal independently. A renewable lease prevents normal overlapping maintenance; all work reuses a single connection and passes real one-/two-connection pool concurrency regressions.
- Native administration exposes the default 365-day policy, read-only storage scope, backlog and last cleanup result. A host scheduler runs bounded batches every five minutes. Age starts at server-observed successful completion; active, failed, uncertain and unknown-completion jobs remain protected.
- Release publication requires build/security/CodeQL checks, verified artifact promotion and build provenance. Packaged QBit metadata uses the JAR's real Implementation-Version.
- Shared submission admission enforces configurable atomic device/tenant limits for outstanding work, retained bytes and hourly allocations. Durable uploads remain charged until confirmed cleanup; matching receipts replay even at capacity. Legacy unknown uploads conservatively reserve 20 MiB.
- Cumulative printer limits prevent rotating identities from growing history indefinitely. Management pages remain bounded, with optional opaque cursors; approval, metadata and job references survive rejected snapshots. A narrow index avoids PostgreSQL limits on wide Unicode names.

## Evidence and migration

The gate exercises real H2 persistence and bounded pools, QQQ StorageAction with an in-memory backend, native process review/resume, current-session record security and real QApplicationJavalinServer route registration/authentication over loopback. Failure tests cover partial upload/deletion recovery, per-document commit boundaries, conflicting/foreign references, destination retargeting, overlapping cleanup and original-content expiry during retry replay. The built JAR manifest reports 0.1.4-rc.1.

Separate disposable S3-compatible fixtures exercise the actual QQQ S3StorageAction and AWS SDK. Windows and Linux same-platform controls each passed 65 checks, including PDF/ZPL, multipart upload, integrity, tenant separation and retention. A controlled Windows-to-Linux migration then reproduced the RC.20 path defect: the old binding matched, reads returned S3 404, and cleanup marked content unavailable while the original Windows-key object remained.

The corrected runtime rejects that migration with HTTP 409 for reads and retries and a recorded cleanup error with zero removals. A native SDK transmission observer, checked against a successful HEAD request, recorded zero requests for the refused read, retry and cleanup. The original object, content availability, tenant/device byte accounting and job/admission/orphan counts remained unchanged. Golden binding tests and a regression for the reproduced multiline-prefix collision also pass. This qualifies refusal of the incompatible layout; it does not implement portable upstream keys or historical-object migration.

H2 2.4.240 fixes the observed close-time compaction schema loss. Exact earlier CI artifacts passed native authentication/query/denial checks, an actual scheduled retention tick, forced termination and cold restart, plus a separate graceful registered-hook shutdown. Independent read-only inspection before application initialization preserved all required tables, settings and counts. These results remain tied to their tested artifacts; they do not qualify Windows reboot or unattended supervision.

Schema initialization adds consumed-enrollment receipts, storage references/content availability, completion timestamps, retention settings/lease and upload intents. Existing inline bytes are retained; completion dates are backfilled only from durable successful events. No automatic inline-to-S3 copy or live purge occurs. Schema changes should be qualified against a backed-up deployment database before rollout.

Admission accounting also backfills retained bytes and recent allocations. Stop older writers before this migration; mixed-version writers bypass accounting and are unsupported. Regression cases cover concurrent tenant admissions, retained terminal payloads, replay at capacity, failed cleanup, unknown legacy uploads, rotating inventory and long-name pagination. See [operations](OPERATIONS.md) for configurable limits and recovery.

## Remaining boundaries

Production S3 endpoints, IAM/bucket policies, external bucket users, PostgreSQL, multi-node lease-expiry behavior, remote TLS deployment and sustained 10,000-print/day throughput are not qualified by these tests. The private native scheduler check is separate from live deployment. SQL and object deletion are not one transaction; crashes between them require idempotent recovery. S3 versioning and unfinished multipart parts have separate lifecycle semantics. See [storage and retention](STORAGE-AND-RETENTION.md).

The completed independent deep scan covers the frozen pre-audit baseline, not the subsequently added storage feature. Its two server findings were remediated and received a fresh independent bypass/regression review; that review's wide-index compatibility finding was corrected before the final gate. Separate review and regressions cover the new storage boundaries. These results do not prove absence of defects or qualify the live deployment boundaries above. No numerical quality score is assigned.
